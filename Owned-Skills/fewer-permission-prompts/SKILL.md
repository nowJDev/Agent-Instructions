# 반복 승인 줄이기.

자주 썼다는 이유만으로 권한을 넓히지 않고 실제 동작이 확인된 최소 후보를 다룬다.

## 입력과 대상 확인.

- 사용자 요청에서 대상 클라이언트·프로젝트·설정 범위·조회만인지 적용까지인지 확인한다.
- Claude Code와 Codex의 규칙 형식은 다르다. 설치 목록으로 대상 앱을 추정하지 않는다.
- 현재 앱의 공식 권한 문서·schema·설정 우선순위·관리 정책과 가용 검증 도구를 확인한다.
- 사용자에게 허용된 현재 대화/트랜스크립트만 분석하고 무관한 세션·개인 설정·토큰을 수집하지 않는다.
- 공유 프로젝트 설정과 개인 로컬 설정 중 요청 범위에 맞는 파일을 선택한다. 전역 확장은 명시 요청에 한정한다.

## 후보 선정.

1. 같은 명령/도구를 정규화해 빈도와 실제 인자, 사용 목적, 허용 시 반복 가능한 범위를 정리한다.
2. 이름이 read/get/list여도 실제 도구 역할과 데이터 접근·외부 전송·인증 영향을 확인한다.
3. 변경·삭제·배포·push·메시지 전송·비밀 읽기·임의 스크립트 실행은 자동 허용 후보에서 제외한다.
4. 셸 연결·리다이렉션·명령 치환·별칭·가변 인자를 포함한 호출은 명령 전체의 부작용을 확인한다.
5. 읽기 전용 후보별로 빈도·정확한 패턴·허용되는 호출·계속 승인받을 반례를 제시한다.
6. 이력이 없거나 실제 도구 역할을 확인할 수 없으면 패턴을 지어내지 않고 후보 부족을 보고한다.

## 최소 규칙 적용.

- Claude는 [공식 권한 문서](https://code.claude.com/docs/en/permissions)의 현재 패턴 문법으로 해당 allow 항목만 병합한다.
- Codex는 [공식 rules 안내](https://developers.openai.com/codex/rules)에 따라 지원되는 좁은 실행 규칙과 검사 방법을 사용한다.
- Claude의 `permissions.allow`를 Codex 설정에 넣지 않는다. 앱별 MCP 규칙도 실제 지원·서버·도구 이름을 확인한다.
- 변경 전 대상 전체를 읽어 백업한다. 기존 allow·deny·ask·관리 제약과 알 수 없는 키를 보존한다.
- 후보와 같은 범위가 승인됐으면 개별 규칙만 추가한다. 조회/제안만 요청됐다면 설정은 변경하지 않는다.
- `Bash(*)`·서버 전체 MCP wildcard·`approval_policy=never`·sandbox 해제 같은 일괄 완화는 이 스킬로 수행하지 않는다.
- 기존 deny/ask와 충돌하면 삭제해 통과시키지 않고 충돌과 실제 우선순위를 보고한다.

## 실패와 결과 증거.

- JSON/TOML은 저장 전후 파싱하고 해당 앱의 현재 schema를 대조한다. rules는 앱의 규칙 검사기를 사용한다.
- Codex의 `codex execpolicy check`가 가용하면 추가한 허용 명령과 비허용 반례를 함께 검사한다.
- 실제 승인창 확인은 안전한 조회로 수행한다. 권한 검증을 위해 쓰기·전송 명령을 실행하지 않는다.
- 파싱·정책·검사 실패 시 이번 변경만 복구하고 원인을 보고한다. 더 넓은 패턴으로 우회하지 않는다.
- 자동 승인 불가가 관리 정책 때문이면 그 제약을 명시하고 설정 변경 성공으로 보고하지 않는다.
- 결과에 후보 근거·적용 파일/개별 규칙·백업·파싱/규칙 검사·실제 승인 동작의 확인 여부를 남긴다.
- 로그·설정의 비밀값은 출력하거나 커밋하지 않는다. 적용하지 않은 후보와 남은 승인 범위를 짧게 적는다.
