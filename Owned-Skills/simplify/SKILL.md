# 동작을 보존하는 단순화.

## 범위와 계약.
- 사용자가 지정한 파일·diff를 대상으로 한다. 미지정이면 최근 변경 범위와 관련 호출자를 확인하고 작업 범위를 명시한다.
- 대상 파일 전체, 공개 인터페이스·호출자·테스트를 읽고 현재 입력·출력·예외·부작용·성능 요구를 파악한다.
- 프로젝트 스타일과 설치된 `design-driven-delivery`가 있으면 따른다. 없어도 범위·계약·계획 확인 후 최소 변경을 검증하며 기존 사용자 변경을 단순화 대상으로 섞지 않는다.

## 절차.
1. 정리 전 필요한 기존 검사를 실행해 기준선을 기록한다. 실패가 있으면 원인을 확인하고 기존 실패를 명확히 남긴다.
2. 읽기 어려운 조건·중복·이름·불필요한 계층 중 실제 이해를 방해하는 것을 고른다. 줄 수나 취향만으로 전체 구조를 바꾸지 않는다.
3. 기존 공통 구현→표준 기능→설치된 의존성 순으로 재사용을 검토한다. 몇 줄을 줄이기 위한 새 의존성·추상화·옵션은 만들지 않는다.
4. 한 번에 이해 가능한 최소 변경을 적용한다. 외부 호출 시점·반복 횟수·평가 순서·예외 종류·async 경계·캐시 수명·취소/정리·자원 소유권을 보존한다.
5. 공개 이름이나 import/export를 바꾸면 모든 소비자와 호환성 영향을 확인한다. 단순화만으로 호출 계약을 바꿔도 된다고 가정하지 않는다.
6. 해당 정상·실패·경계 검사를 실행한다. 원래 예외와 부작용 순서가 같고 테스트가 수정 없이 통과하는지 비교한다.
7. 실패하면 이번 최소 변경의 원인을 조사하고 필요한 부분만 복구한다. 테스트를 지우거나 오류 처리를 약화해 통과시키지 않는다.
8. diff 전체·호출자를 정확성·구조·오류·보안·성능 관점으로 다시 읽고 `code-review`가 있으면 적용한다. 결과가 더 읽기 어렵거나 범위를 넓혔으면 이번 변경만 단순한 쪽으로 되돌린다.

## 발견과 종료.
- 새로운 버그를 발견하면 단순화와 구분해 증거를 보고한다. 수정까지 요청 범위에 있을 때만 근본 원인 수정과 별도 검증을 수행한다.
- 이미 명료한 부분은 변경하지 않는다. 의미 없는 래퍼·설정·주석을 추가해 정리를 설명하지 않는다.
- 결과에는 이해하기 쉬워진 구체적 이유, 바뀐 파일, 보존한 계약과 실제 검사 결과를 적는다.
- 성능이나 실제 환경을 확인하지 못했다면 해당 한계를 남긴다. 줄 수 감소를 정확성·속도 개선의 증거로 쓰지 않는다.
