# 기능 개발.

## 입력과 범위.
- 사용자 요청, 작업 루트, 적용 지침, 현재 변경 파일과 완료 조건을 확인한다. 이미 답한 요구사항이나 승인된 설계는 재사용한다.
- 설치된 `design-driven-delivery`가 있으면 그 단계 안에서 사용한다. 없어도 조사→요구사항·설계·계획 확정→격리 구현→검증·리뷰 순서를 지킨다. 이미 확보한 승인·계획을 중복 요청하지 않는다.

## 진행.
1. Git 상태와 기존 실행·검증 명령을 읽기 전용으로 확인한다. 사용자 미커밋 변경과 이번 변경의 경계를 기록한다.
2. 유사 기능의 진입점부터 호출자, 데이터 흐름, 실패 처리, 테스트·fixture·설정·export까지 추적한다. 검색에는 `rg`를 우선하고 수정할 파일은 전체를 읽는다.
3. 현재 문제와 원하는 동작을 정상 입력·실패 입력·기존 사용자 영향으로 적는다. 결과를 바꾸는 불확실성만 질문하고 독립 조사는 계속한다.
4. 기존 패턴을 재사용하는 최소 변경과 필요한 대안을 비교하고 요구사항·설계·파일별 구현·검증 계획을 확정한다. 설치된 `brainstorming`·`writing-plans`가 있으면 이 단계에서 사용한다.
5. 사용자 변경과 구현을 분리할 격리 상태를 확인한다. 필요한 회귀 테스트로 기존 실패를 관찰하고 근본 원인을 최소 수정해 같은 검사를 통과시킨다. `test-driven-development`·`using-git-worktrees`가 있으면 적용하며, 없으면 프로젝트의 격리·검증 수단으로 같은 증거를 확보한다.
6. 사용자 요청이나 적용 지침이 위임을 허용하고 가용 위임 도구가 있으며 독립 조사에 이득이 있을 때만 역할을 나눈다. Claude 전용 에이전트 이름이 없어도 같은 검토 관점으로 순차 수행할 수 있다. 반환된 핵심 파일은 직접 확인한다.
7. 영향 있는 테스트·회귀·타입·빌드를 실행하고 정상·실패 사용자 흐름을 실제 관찰한다. `verify`가 있으면 적용한다. 실패 시 전체 오류·재현 조건·변경 원인을 조사하고 증거에 맞춰 고친다. `systematic-debugging`이 있으면 이때 사용한다.
8. 전체 파일·호출자·diff를 요구사항·정확성·구조·보안·성능 관점에서 검토하고 문서를 실제 결과에 맞춘다. `code-review`가 있으면 사용한다. Git 통합·외부 게시·메시지는 요청된 범위에서만 수행한다.

## 실패와 종료.
- 새로운 요구사항·설계 충돌을 구현으로 덮지 않는다. 조사 결과와 영향을 설명하고 영향을 받지 않는 작업을 계속한다.
- 테스트 실패나 미확인 사용자 흐름을 완료로 바꾸지 않는다. 생략된 검사와 이유를 명시한다.
- 결과에는 바뀐 동작, 수정 파일, 실행한 명령·종료 코드, 관찰 증거와 남은 제한을 포함한다.
