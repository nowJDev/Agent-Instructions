# FigJam 프로젝트 계획.

## 입력과 가용성.
- PRD·대상 파일 또는 새 파일·읽어도 되는 코드 진입점·작성 범위를 확인한다.
- 실제 Figma 도구와 인증·팀 선택 기능이 노출됐는지 확인한다. 카탈로그에 이름이 있다는 이유로 사용 가능하다고 가정하지 않는다.
- 새 파일 전 `figma-create-new-file`, API 편집 전 `figma-use`와 `figma-use-figjam`, 다이어그램 전 `figma-generate-diagram`의 가용성과 필수 절차를 확인한다. 필요한 스킬이나 도구가 없으면 임의 API 호출로 우회하지 않고 로컬 초안까지만 준비한다.

## 절차.
1. PRD 전체와 지정 코드 경계를 읽고 목표·비목표·사용자·성공 기준·의존성·단계·위험을 추출한다. 소유자나 수치를 지어내지 않고 확인할 항목으로 구분한다.
2. 목표·범위, 사용자·성공 기준, 단계·일정, 의존성, 위험·확인 질문 중 실제 내용이 있는 섹션만 제안한다. 사용자가 고른 섹션이 0개면 파일을 만들지 않고 종료한다.
3. 섹션별 내용과 표·메모·다이어그램 형식을 보여주고 사용자의 선택·기존 승인을 반영한다. 승인되지 않은 내용을 외부 보드에 쓰지 않는다.
4. Figma 도구·인증 또는 필요한 필수 스킬이 없으면 섹션별 Markdown 표와 필요한 Mermaid 초안을 채팅 또는 요청한 로컬 파일로 준비한다. Figma 파일은 미생성이라고 명시하고 연결 설정을 임의 변경하지 않는다.
5. 기존 파일 편집 요청이면 지정 URL·fileKey·페이지·수정 허용 노드를 확인하고 원본의 새 파일 생성 단계를 생략한다. 새 파일이 요청된 경우에만 대상 팀과 생성 범위를 확인해 파일을 만들고 URL·편집기 타입·대상 페이지를 검증한다. 이후 모든 확인은 현재 대상 범위에 맞춰 수행한다.
6. 스켈레톤→섹션별 채우기→다이어그램 순서로 작은 변경을 수행한다. 실제 폰트·팔레트·좌표는 사용자 디자인 규칙과 설치된 필수 스킬을 따른다. 조회로 확인한 편집기·페이지·API만 사용하고 고정 레이아웃을 추정하지 않는다.
7. 다이어그램 생성 호출 직전에 현재 페이지의 자식 ID 집합을 저장한다. 호출 직후 차집합과 반환된 생성 ID를 교차 확인해 이번 호출이 만든 노드만 이동·재생성한다. 기존 노드·타 작업 노드·이전 실패 잔여물을 페이지 전체에서 선택하지 않는다. 소유 ID가 불명확하면 이동·삭제하지 않고 상태를 보고한다.
8. 각 쓰기에서 생성·변경한 노드 ID를 기록하고 실제 스크린샷으로 겹침·잘림·빈 섹션·라벨을 확인한다. 조회값만으로 시각 검증을 대신하지 않는다.
9. 오류 시 일부 변경이 남았을 수 있으므로 실제 노드 상태와 기록 ID를 먼저 확인한다. 확인 없이 같은 내용을 재생성하거나 기존 보드를 삭제하지 않는다.
10. 최종 전체 보드를 관찰하고 PRD의 선택 섹션·목표·의존성과 대조한다. 누락·실패 섹션은 미완료로 보고한다.

## 결과.
- 파일 URL 또는 로컬 초안 경로, 선택 섹션과 검증한 화면, 생성·변경 ID, 미검증 범위를 보고한다.
- 사용자가 취소하면 즉시 중단하고 이미 만든 파일·노드의 상태를 알린다. 취소를 전체 삭제 허가로 해석하지 않는다.
- 호스트 전용 도구명은 실제 제공 기능으로 매핑한다. 오류가 원자적이거나 특정 도구가 항상 있다고 가정하지 않는다.

## 공개 참고.

[공식 API·MCP 문서](references/sources.md)는 실제 API와 지원 범위를 확인할 때 읽는다. 타사 스킬 원문·로컬 플러그인 파일은 이 패키지에 포함하지 않는다.
