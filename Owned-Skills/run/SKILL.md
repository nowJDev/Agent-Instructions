# 실제 실행.

## 입력과 실행 계획.
- 프로젝트 루트, 실행할 기능, 입력·URL·기대 결과, 계속 켜둘지 검증 후 종료할지를 확인한다.
- 지침·README·manifest·lockfile·CI·실행 스크립트를 읽고 실제 실행 명령과 작업 디렉터리를 고른다. 서버가 필요 없는 CLI·라이브러리에 서버를 만들지 않는다.
- 사용자 코드·기존 변경을 보존한다. 실행 요청을 의존성 업그레이드·설정 변경·배포 권한으로 확대하지 않는다.

## 실행.
1. 설치된 런타임·의존성과 필요한 환경변수 이름·서비스를 확인한다. 비밀 값은 출력하지 않는다. 전제가 없으면 부족한 조건을 보고하고 가능한 로컬 검사를 구분한다.
2. 같은 프로젝트의 기존 프로세스·포트·URL을 확인한다. 다른 앱의 포트나 기존 서버를 강제 종료하지 않는다. 재사용하면 코드·작업 디렉터리·버전이 맞는지 확인한다.
3. 필요한 명령을 해당 디렉터리에서 실행하고 프로세스·세션 ID, 시작 명령, 로그 위치를 기록한다. Windows 백그라운드 도우미는 별도 창을 요청하지 않았으면 숨겨 실행한다.
4. 서버는 준비 로그만 보지 않고 실제 요청의 상태와 응답을 확인한다. 프로세스가 살아 있어도 HTTP 500·예상 응답 불일치·시작 오류면 성공이 아니다.
5. 웹 UI는 실제 제공되는 Chrome DevTools를 우선하고 요청된 브라우저가 있으면 그것을 쓴다. 렌더된 DOM을 읽고 요청된 사용자 동작을 수행해 결과·콘솔·네트워크 오류를 관찰한다.
6. CLI는 정상 입력과 필요한 실패 입력을 실행해 stdout·stderr·종료 코드가 기대 동작과 맞는지 확인한다. exit 0만으로 비즈니스 결과가 맞다고 판단하지 않는다.
7. 라이브러리는 실제 소비 예제·단위 테스트·공개 import로 확인한다. TUI·데스크톱 앱은 지원되는 터미널/화면 제어로 관찰하고, 제어 도구가 없으면 시작 확인과 실제 UI 미검증을 구분한다.
8. 요청된 최소 확인을 마치면 검증용으로 직접 만든 프로세스만 종료한다. 사용자가 계속 사용하려고 실행을 요청했다면 유지 상태·URL·자체 프로세스 ID와 중지 방법을 알려준다. 기존 사용자 서버는 유지한다.

## 실패와 증거.
- 준비 대기는 정해진 시간 안에서 응답·로그를 확인한다. 근거 없는 고정 지연이나 무한 재시도로 시작 실패를 숨기지 않는다.
- 실패한 명령·오류·조건을 읽고 원인을 구분한다. 검증만 요청이면 코드를 바꾸지 않는다. 수정까지 승인됐으면 근본 원인 수정 후 관련 검사만 재실행한다.
- 결과에 실행 위치·정확한 명령·사용한 입력/URL·관찰한 응답·종료 코드·남은 프로세스를 포함한다.
- 접근·인증·입력 도구가 없어 실제 동작을 보지 못했다면 그 범위를 명시한다. 터미널 시작 로그만으로 화면 동작 완료를 보고하지 않는다.
- 설치된 verify와 verification-before-completion이 있으면 완료 판정에 적용한다. 없으면 요구사항별 통과·실패·미검증을 현재 실행 증거와 대조한다. 요청한 핵심 동작을 재현하지 못했거나 실패 검사가 남으면 전체 완료를 주장하지 않는다.
