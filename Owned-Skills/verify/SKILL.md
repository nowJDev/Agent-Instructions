# 실제 동작 검증.

## 검증 계약.
- 무엇이 바뀌었고 어떤 입력·상태·사용자 행동에서 무엇이 보여야 하는지 요청과 설계·코드·테스트에서 확인한다.
- 정상·실패·경계 조건의 기대 결과와 필요한 실행 환경을 짧게 기록한다. 구현 코드의 현재 결과를 기대값으로 삼지 않는다.
- 검증만 요청이면 코드를 바꾸지 않는다. 수정 요청이 계속 유효하면 발견한 결함은 원인 조사와 승인 범위의 수정으로 연결한다.

## 실행과 대조.
1. 설치된 verification-before-completion이 있으면 적용한다. 없어도 현재 변경에 대해 검사를 실제로 실행하고 전체 출력·종료 코드·관찰 결과를 확인한 뒤에만 성공을 말한다. 변경된 파일 전체·호출자와 기존 사용자 변경의 경계를 확인한다.
2. manifest·CI·README에서 실제 검사 명령을 고른다. 대상 테스트→관련 회귀→필요한 전체 테스트·타입·린트·빌드를 변경 영향에 맞게 실행한다.
3. 프로젝트에 없는 도구·커버리지 80% 같은 새 기준을 강제하지 않는다. 검사 명령이 없으면 행동을 관찰할 최소 재현을 만들거나 미검증을 보고한다.
4. 설치된 run이 있으면 실제 앱·CLI·라이브러리 실행에 사용한다. 없어도 프로젝트 문서의 명령·실행 위치·전제를 확인해 실행한다. 기존 서버는 코드·버전·작업 위치가 맞을 때만 재사용하고 기존 프로세스를 종료하지 않는다. 자체 시작 프로세스 ID를 기록한다. 서버는 실제 HTTP 상태·응답을, CLI는 입력별 출력·종료 코드를 확인한다. 웹 UI는 가용 화면/브라우저 도구로 요청한 사용자 행동을 실제 수행해 결과·에러·네트워크·화면을 확인한다. 도구가 없으면 시작 확인과 UI 미검증을 구분한다.
5. 정상 입력과 요청된 실패 입력을 기대 결과와 대조한다. lint·컴파일·exit 0은 저장·계산·인증 동작 성공의 대체 증거가 아니다.
6. 변경 전 실패 재현이 필요한 버그라면 기존 증상과 수정 후 결과를 같은 조건으로 비교한다. 테스트를 삭제하거나 기대값을 현재 결함에 맞춰 성공시키지 않는다.
7. 실패한 검사와 환경 문제를 구분하고 전체 오류를 확인한다. 실행하지 못한 검사를 통과 수에 포함하지 않는다.
8. 직접 만든 임시 파일·프로세스만 요청 범위에서 정리하고 기존 데이터·세션·서버는 보존한다.

## 판정과 보고.
- 요구사항별로 통과·실패·미검증을 기록한다. 명령·실행 위치·입력·관찰 결과·종료 코드·테스트 총수/실패/skip을 근거로 남긴다.
- 재현되지 않은 핵심 사용자 흐름이나 실패 검사가 남으면 전체 완료를 주장하지 않는다. 가능한 부분과 막힌 조건을 구분한다.
- 비밀 값이 포함될 수 있는 로그·보안 검색은 값 대신 위치·유형만 보고한다.
- 설치된 code-review로 연결할 때는 전체 변경 범위와 증거를 전달한다. 없으면 변경 파일 전체·호출자·테스트에서 정상/실패 경로와 기존 계약을 직접 검토하고 파일·줄·재현 조건·영향을 남긴다. 검사 성공은 외부 게시·병합·배포 권한이 아니다.
- 결과는 바뀐 동작, 핵심 검증 근거, 남은 제한 순서로 짧게 제시한다.
