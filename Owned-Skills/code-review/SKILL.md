# 코드 리뷰.

읽기 전용 진단이 기본이다. 리뷰 요청만으로 수정·커밋·PR 게시·메시지 전송 권한을 얻지 않는다.

## 입력과 도구 확인.

1. 대상 저장소와 변경 범위를 정한다. 인자가 없으면 현재 워킹트리의 staged·unstaged·untracked 변경을 모두 확인한다.
2. 로컬은 Git, `rg`, 전체 파일 읽기 도구를 사용한다. PR은 사용 가능한 GitHub 읽기 도구 또는 인증된 `gh`를 확인한다.
3. `git status --short`, `git diff --stat`, `git diff --cached --stat`으로 범위를 기록한다. 새 파일은 별도로 읽는다.
4. 브랜치·PR 리뷰는 기준과 대상 SHA를 확정한다. PR 파일은 대상 SHA의 전체 본문을 읽어 워킹트리와 섞지 않는다.
5. 대상이 모호해 결론이 달라지면 한 번 질문한다. 변경 리뷰에서 변경이 없으면 그 사실을 보고한다. 다만 파일·증상·진단 대상이 명시됐으면 Git 변경이나 저장소가 없어도 해당 코드 전체·호출자·테스트로 현재 동작을 검토한다.

## 실제 검토.

1. 적용 지침, 요구사항, 관련 테스트·검증 명령을 읽는다. 변경 파일은 처음부터 끝까지 읽는다.
2. `rg`로 변경 함수의 호출자, 인터페이스·export, 설정·fixture와 데이터 흐름을 찾는다.
3. 정상 입력·빈 값·실패·재시도·동시성·권한 경계에서 기존 계약이 보존되는지 추적한다.
4. 정확성, 가독성·재사용, 구조 경계, 보안, 성능을 변경 영향에 맞게 검토한다.
5. 문제마다 재현 조건과 사용자 영향, 근거 위치를 확인한다. 취향·파일 길이만으로 결함 판정을 만들지 않는다.
6. 테스트가 올바른 동작과 실패 경로를 관찰하는지 본다. 테스트 통과를 코드가 옳다는 유일한 근거로 쓰지 않는다.
7. 실행이 필요하면 저장소에 정의된 최소 검사만 수행한다. 설치·네트워크·데이터 변경이 필요한 검사는 기존 권한을 먼저 확인한다.
8. 해결책은 기존 공통 구현에서 가장 작은 변경을 제안한다. 실제 수정은 명시적으로 요청받은 범위에서만 별도 변경 절차로 수행한다.

## 실패와 불확실성.

- 파일·PR·도구에 접근할 수 없으면 원인과 미검토 범위를 보고한다. 없는 내용을 추정해 검토하지 않는다.
- 검사가 실패하면 전체 오류에서 원인을 찾고 기존 실패인지 이번 변경인지 구분한다.
- 근거가 부족한 의심은 확인할 질문으로 남긴다. 깊이 요청이 높아도 저확신 추정을 확정 결함에 섞지 않는다.
- `--comment`, `--fix` 같은 문자열을 하네스 기능으로 가정하지 않는다. 실제 사용자 요청과 사용 가능한 도구로 권한·지원 여부를 판별한다.
- 서브에이전트는 사용자의 병렬 검토 요청이나 적용 지침이 허용할 때만 사용한다.

## 증거 출력.

- 심각도 순서로 파일·줄, 재현 조건, 실제 영향, 근거, 최소 수정안을 제시한다.
- 확정 결함과 선택적 단순화 제안을 구분하고 중복 발견을 합친다.
- 실행한 검사와 결과, 읽지 못한 범위, 남은 위험을 적는다. 결함이 없으면 검토 범위 안에서 발견하지 못했다고 표현한다.
- 비밀 값·인증 헤더·개인 데이터를 인용하지 않고 위치와 유형만 보고한다.
