# 상태 변경 워크플로.

## 목차.

1. 공통 원칙.
2. DISCOVERED.
3. DISCUSSING.
4. DESIGN_APPROVED.
5. PLAN_APPROVED.
6. IMPLEMENTING.
7. VERIFIED.
8. REVIEWED.
9. DOCUMENTED.
10. COMMITTED.
11. INTEGRATED.
12. 되돌아가기.

## 1. 공통 원칙.

- 프로젝트 지침과 사용자 요구를 일반 절차보다 우선한다.
- 최대 3개 연속 작업 후 결과를 확인한다.
- 현재 단계의 증거 없이 다음 단계로 이동하지 않는다.
- 기존 코드·문서·테스트와 다른 결과가 나오면 중단하고 원인을 확인한다.
- 여러 독립 기능이 섞이면 별도 설계·계획·커밋으로 분리한다.

## 2. DISCOVERED.

다음을 확인한다.

- 루트와 하위 `AGENTS.md`.
- 저장소, 브랜치, Worktree, upstream과 변경 파일.
- 최근 커밋과 현재 기준선.
- 관련 코드·문서의 기존 해결책과 호출자·테스트·fixtures·설정·exports의 변경 영향.
- 사용자 변경, 보호 경로, 시크릿과 대용량 파일.
- 사용 가능한 테스트·빌드·실행 방법.

수정할 파일은 변경 전에 처음부터 끝까지 읽는다. 조사 결과로 요청 범위와 영향을 설명한다.

## 3. DISCUSSING.

새 기능이나 동작 변경이면 `brainstorming`을 사용한다.

- 질문은 한 번에 하나씩 한다.
- 목적, 비목표, 사용자와 실제 정상·실패 사례를 확인한다. 완료 조건은 사용자 행동·입력 조건·기대 결과·확인 방법으로 작성한다.
- 용어의 모호함이 결과를 바꾸면 기존 정의와 대조해 확인하고, 확정된 용어와 중요한 결정의 이유를 기존 설계 문서에 기록한다. 기록할 내용이 있을 때만 필요한 항목을 작성한다.
- 2~3개 접근법과 트레이드오프를 제시한다.
- 추천안을 설명한다.
- 아키텍처, 데이터 흐름, 수명, 오류와 검증을 섹션별로 승인받는다.

## 4. DESIGN_APPROVED.

승인된 설계를 기존 프로젝트의 설계 경로에 저장한다.

설계에 다음을 포함한다.

- 목표와 비목표.
- 기준선과 문제 정의.
- 사용자 흐름.
- 책임과 경계.
- 정상·실패·중단·재시작 경로.
- 자동·수동 검증.
- 보안·라이선스·배포 영향.
- 완료 조건.

placeholder, 모순, 정의되지 않은 개념과 요청 밖 확장을 제거한다.

## 5. PLAN_APPROVED.

`writing-plans`를 사용해 승인 설계를 실행 계획으로 변환한다.

각 Task에 다음을 기록한다.

- 정확한 파일 경로.
- 먼저 작성할 실패 테스트.
- 예상 RED.
- 최소 구현.
- 예상 GREEN.
- 대상·전체 회귀.
- 수동 검증.
- 문서와 커밋 단위.

사용자 승인이나 기존 계획의 명시적 실행 요청을 받은 뒤 구현한다.

## 6. IMPLEMENTING.

Git 프로젝트면 `using-git-worktrees`로 격리 상태를 확인한다.

- 기존 작업 트리와 사용자 변경을 보존한다.
- 기능·버그 수정은 `test-driven-development`를 따른다.
- 실패가 예상과 다르면 `systematic-debugging`으로 원인을 조사한다.
- 프로젝트의 기존 구현·패턴 → 표준 라이브러리·플랫폼 기능 → 설치된 의존성·연결 도구 순으로 요구사항 충족 여부를 확인하고, 요청한 문제를 해결하는 최소 변경을 유지한다. 충족하면 추가 외부 검색·설치를 강제하지 않는다.
- Task 완료 때 관련 계획 체크박스와 증거를 갱신한다.

## 7. VERIFIED.

`verification-before-completion`을 사용한다.

- 변경 동작의 대상 테스트를 실행한다.
- 프로젝트 전체 회귀를 실행한다.
- 정적 검사, 빌드와 패키징을 확인한다.
- 실제 앱·기기·운영 환경이 필요하면 수동 검증한다.
- 총 테스트, 통과, 실패, 스킵과 로그 경로를 기록한다.
- 테스트 산출물과 의도하지 않은 변경을 제거한다.

## 8. REVIEWED.

`code-review`를 사용해 승인 기준선부터 전체 변경을 검토한다.

- 정확성과 상태 오류.
- 재사용·단순화.
- 효율성과 성능.
- 수명과 정리.
- 실패 격리.
- 보안과 배포 경계.
- 테스트 신뢰성.
- 문서와 주석 정합성.

차단·중요 발견을 해결하고 관련 검증을 다시 실행한다.

## 9. DOCUMENTED.

다음을 실제 상태에 맞게 갱신한다.

- 승인 설계.
- 구현 계획 체크박스.
- 진행 체크리스트.
- 현재 상태.
- 코드 리뷰 감사.
- 운영·배포·라이선스 문서.
- 필요 시 handover.

문서와 코드가 다르면 완료하지 않는다.

## 10. COMMITTED.

- `git diff`와 `git diff --check`를 확인한다.
- 사용자 변경과 보호 경로가 스테이징되지 않았는지 확인한다.
- 관련 코드·테스트·문서를 한 논리 단위로 스테이징한다.
- 프로젝트 규칙에 맞는 커밋 메시지를 사용한다.
- 커밋 후 `git status`와 `git show --stat`을 확인한다.

## 11. INTEGRATED.

`finishing-a-development-branch`를 사용한다.

- 원격 최신 상태와 분기 관계를 확인한다.
- 사용자에게 승인된 방식으로 병합 또는 PR을 수행한다.
- force push를 사용하지 않는다.
- 병합·푸시 후 로컬과 원격 해시를 비교한다.
- 에이전트가 만들지 않은 Worktree를 임의로 제거하지 않는다.

## 12. 되돌아가기.

다음 상황에서는 이전 단계로 돌아간다.

- 요구사항 해석이 바뀜 → `DISCUSSING`.
- 아키텍처나 성공 기준이 바뀜 → `DESIGN_APPROVED` 이전.
- 계획에 파일·테스트 누락이 발견됨 → `PLAN_APPROVED`.
- 테스트가 예상과 다르게 실패함 → 진단 후 `IMPLEMENTING`.
- 리뷰에서 동작 결함이 발견됨 → 테스트 RED 후 `IMPLEMENTING`.
- 수동 검증이 실패함 → 상태를 미완료로 유지하고 원인 조사.
